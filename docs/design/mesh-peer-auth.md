# wss ピア間相互認証プロトコル

- 起草: kawaz (2026-09-07)。ccmsg の instance 間 mesh ([契約の Instances and mesh](https://github.com/kawaz/ccmsg-protocol/blob/main/docs/DESIGN.md)) の認証に適用する

mesh ノード間で、相互に信頼できるチャンネルを、管理対象を増やさずに確保する。本書は Web PKI をその基盤に選んだ場合の設計である。

---

## 1. 目的

mesh ノード間で相互に信頼できるチャンネルを確保する。かつ、そのために管理するものを増やさない。後者は前者に従属する制約ではなく、同格の目的である。

管理するものとは、配布・更新・保管・復旧といった手順を必要とするものなどを指す。鍵素材、証明書、ノードごとに異なる設定などがこれにあたる。

## 2. 解きたい問題

チャンネルが相互に信頼できるとは、両端がそれぞれ、通信相手が設定上のどのピアであるかを特定できていることである。

接続しただけでは、どちらの端も相手が何者か分からない。名乗りは検証できず、クライアント IP の逆引きは信用に値しない。相手を設定上のピアに対応づける手段が要る。

## 3. 前提条件

| # | 条件 | 満たさない場合 |
|---|---|---|
| P1 | 接続がステートフルである (長命な全二重セッション) | 本プロトコルは成立しない (§9) |
| P2 | 各ノードが公開 FQDN と有効な TLS 証明書を持つ | 信頼の根が存在しない |
| P3 | 各ノードが全ピアのエンドポイント URL を設定として持つ | 照合対象がない |
| P4 | 各インスタンスが起動時に自分のエンドポイント URL (`self`) を確定している | `aud` を検証できない (§5.2) |

P1 が本質。接続確立時に一度信頼を確立すれば、以降その接続の同一性は TLS が保証するという性質に全面的に依存する。

P4 の `self` の確定手段は本書の範囲外とする (§5.2)。ccmsg では設定のエンドポイント一覧のうち自分の id を持つ行が `self` になる ([DESIGN.md](../DESIGN.md) §8.2)。

## 4. 信頼モデル

```
   S ──── TLS サーバ証明書 (Web PKI) ────▶ R     S が R を認証
   S ──── JWS (本プロトコル) ───────────▶ R     R が S を認証
```

- 信頼の根は Web PKI。「その FQDN の証明書秘密鍵を現在保持している主体」を正当なピアとみなす
- 認証は接続確立時の 1 回のみ。以降のメッセージの同一性は TLS に依存する
- 1 本の接続で相互認証が閉じる

S 側は、TLS のサーバ証明書検証によって、接続先が設定上のどのピアであるかを知る。追加の手順を要しない。以降の手順が R 側の認証だけを扱うのはこのためであり、S 側が相手を知る必要がないからではない。基盤を差し替える際は、この保証がどこから来ていたかを確認すること。

信頼境界は双方の TLS 終端点の間である。終端がアプリケーションプロセス自身か、前段の LB かリバースプロキシかは本プロトコルの関知するところではない。終端より内側 (LB ↔ アプリ間など) の完全性は、そのネットワークを運用する側の責務として本プロトコルのスコープ外とする。

したがって、本プロトコルが R に与える保証は「この接続は S の TLS 終端点を通って来た」である。それがアプリまで無改竄で届くかは別の保証であり、内部区間も TLS 化されているのが望ましいが、要件としては課さない。

### 4.1 脅威モデル

排除するのは第三者だけではない。正規ピアによる他ピアへのなりすましも排除する (`aud` による。§5.3)。TLS の片側認証で消えるのは見知らぬ第三者であって、内部の別ピアではない。

排除しないもの:

- 権限分離。本プロトコルが答えるのは「誰か」だけで、「何をしてよいか」は上位レイヤ
- ホストを掌握された正規ピア。信頼の根が Web PKI である以上、FQDN を制御する者は正当なピアである

### 4.2 認証粒度 (origin ではなく URL)

TLS が認証するのは FQDN までであり、同一 origin 内の別インスタンスを区別しない。`wss://h.example/a` と `wss://h.example/b` は TLS 層から見れば同一の主体である。

本プロトコルは `iss` / `aud` をパスを含む URL の完全一致で相互に検証することで、この粒度差を埋める。結果として 1 つの origin に複数インスタンスを相乗りさせられる。

- `iss` … R は接続元がどのインスタンスかをパスまで含めて確定する
- `aud` … S が `/x` 向けに作った署名を、同一ホストの `/y` に投げ込めない

ただし相乗りするインスタンス同士が互いに信頼境界を成すかは別問題である。同一プロセス内の論理インスタンスであれば `iss` / `aud` は識別子として機能するだけで、境界にはならない。境界とするには最低限、プロセス分離と鍵素材の分離、および §6.3 の鍵配布分離が要る。

## 5. プロトコル

C1 を張ってハンドシェイクを開始した側を S、受けた側を R とする。役割はこの一点で決まり、以降固定される。

C2 は R が dial するため、その時点の dial の向きは S / R の役割とは無関係である。

| | dial する側 | 用途 | 寿命 |
|---|---|---|---|
| C1 | S | mesh の通信路本体。認証対象 | 長命 |
| C2 | R | 鍵と challenge の交換 (§6) | 1 往復で close |

```
 1. C1   S ──▶ R   wss 接続確立 (S は TLS サーバ証明書で R を認証)
 2.      S         エフェメラル鍵ペアを生成し、kid を採番して取得可能にする
 3. C1   S ──▶ R   hello { ver, iss, aud, kid }
 4.      R         iss / aud を設定と照合 (§5.7)。NG なら close
 5. C2   R ──▶ S   接続確立 (R は TLS サーバ証明書で S を認証)
 6. C2   R ──▶ S   jwk_req { kid, challenge }
 7. C2   S ──▶ R   jwk_res { jwk }
 8. C2             close
 9. C1   S ──▶ R   proof (JWS: challenge を署名)
10.      R         署名検証 (§5.7)。NG なら close
11.      R         C1 を「S からのもの」として確定
12. C1   R ──▶ S   ack
13.      S         鍵を破棄。以降メッセージ送信可
```

challenge を jwk_req に相乗りさせているため、challenge のための往復は発生しない。C2 は元々鍵取得のために必要であり、そこに載せている。

C2 で渡した challenge に対する proof は C1 に返る。両者は `kid` で対応づく。R は kid から C1 を引き、S は自分が採番した kid から C1 を引く。

S の鍵は C1 ごとに使い捨てる (§7)。

### 5.1 信頼の連鎖

各手順が何を信頼可能にするかを、誰から見た信頼かとともに追う。

初期状態でどちらも信頼しているのは、設定のエンドポイントリストと CA の 2 つだけである。

S 側:

1. 設定への信頼により、`aud` が接続してよい URL であることを信頼する
2. `aud` の TLS により、C1 を信頼する
3. C1 への信頼により、C1 の接続相手が `aud` であることを信頼する ★

R 側:

1. hello:req の時点では、C1 も req の内容も信頼していない
2. 設定への信頼により、req の `iss` が接続してよい URL であることを信頼する。同時に `aud` が `self` と一致することを確認する
3. `iss` の TLS により、C2 を信頼する
4. C2 への信頼により、jwk_res の `jwk` を信頼する
5. `jwk` と proof の検証により、C1 を信頼する
6. proof への信頼により、C1 の接続相手が `iss` であることを信頼する ★
7. C1 への信頼により、遡及して req の内容を信頼する。これにより req の `kid` が S の採番したものだと確定し、取得した `jwk` が S の用意したものだったことが裏づけられる

S と R がそれぞれの信頼源から手順を踏んで積み上げた結果、★ の 2 点により、C1 の接続相手が誰であるかを相互に確認できている。

R 側の 2 で `iss` の照合と `aud` の確認を同時に済ませているため、S が接続しようとした相手が自分であることは、この時点で既に確定している。proof の検証後に改めて遡及する必要はない。

### 5.2 自己識別

検証する側は自分のエンドポイント URL (`self`) を知っている必要がある。`aud` の照合対象であり、自分が hello を送る際の `iss` でもある。同一の値を両方向で使うため、送信側と受信側で識別がずれない。

`self` の確定手段は本プロトコルの範囲外とする。要件は起動時までに確定していることだけである。

接続やリクエストから自分を逆引きしてはならない。Host ヘッダは接続元が指定する値であり、前段 LB を挟めばパスも書き換わりうる。どちらも自己識別の根拠にならない。

相乗り構成 (§4.2) では、インスタンスごとに異なる `self` を持つ。1 プロセスが複数インスタンスを提供する場合、どのインスタンスとして応答しているかはリスニングソケットからは判別できないため、ハンドラの生成時に `self` を束縛しておく。

`peers` に `self` が含まれていてもよい。mesh 全体へ同一のリストを配り、`self` を除いて接続先とする構成を許す。

### 5.3 hello

署名を持たない。名乗りと、鍵の在り処を伝えるだけである。

```json
{
  "ver": 1,
  "iss": "wss://s.example/mesh",
  "aud": "wss://r.example/mesh",
  "kid": "<128bit random>"
}
```

`iss` はピア識別子とエンドポイント URL を兼ねる。設定内のピアを引く照合キーであり、鍵取得先はそこで引いた設定エントリから導出する。

`ver` は hello と proof のフォーマットを将来変更するための逃げ道。

この時点では何も信頼しない。R は `iss` が設定にあることと `aud` が自分であることだけを確認し、鍵取得に進む。

### 5.4 proof

challenge への署名。これが認証の本体である。

```json
{
  "ver": 1,
  "iss": "wss://s.example/mesh",
  "aud": "wss://r.example/mesh",
  "challenge": "<鍵要求で受け取った値>",
  "exp": 1757000010
}
```

JWS のヘッダに `kid` が入り、hello の `kid` と一致していなければならない。`sub` は置かない (`iss` と同値になり意味がない)。

`iss` / `aud` を hello と重複して持つのは、署名対象に含めるためである。hello は署名されていないので、そこに書かれた値は何も保証しない。

### 5.5 challenge

R は C2 の jwk_req に 128bit 以上のランダムな challenge を相乗りさせる (§6)。S はそれを proof の署名対象に含める。

R が持つ状態は C1 ごとの challenge 1 個であり、proof を受けた時点で消費する。再送も再利用も受け付けない。グローバルなリプレイ記録も期限管理も不要。

過去の署名は challenge が異なるため再生できない。R 側の状態が接続に従属しているため、記録も期限管理も残らない。



### 5.6 各フィールドの役割

hello は署名されていないため、そこに書かれた値は何も保証しない。役割を持つのは proof のクレームである。

| クレーム (proof) | 防ぐもの |
|---|---|
| `iss` | ピアの識別 (照合キー) |
| `aud` | リレー攻撃。正規ピア R′ が S から受けた署名を本物の R に転送してなりすます |
| `challenge` | リプレイ。過去の署名の再生 |
| `exp` | ハンドシェイク段階の寿命の上限 |

`exp` は challenge があれば新鮮さの担保としては冗長だが、接続のタイムアウト設定に依存せずハンドシェイクの寿命を自己完結させるために持つ。接続が先に切れれば proof ごと捨てられ、接続が長生きしても proof は期限切れになる。どちらの経路でも回収されるので、専用のタイマー管理が要らない。

### 5.7 検証ルール

hello 受信時 (鍵取得の前):

1. `ver` が既知であること
2. `iss` が設定内のピアと一致すること。スキーム・ホスト・ポート・パスの完全一致
3. `aud` が設定の `self` と一致すること。同じく完全一致 (§5.2)

ここを通ったら鍵取得に進む。鍵取得は外部への接続を伴うため、安価な照合を先に済ませる。

proof 受信時:

4. `ver`、`iss`、`aud` が hello と同一であること
5. `challenge` がこの接続で出した値と一致すること。一致したら即座に消費する (再送・再利用は不可)
6. `exp` が未来であること
7. 署名検証。`alg` は JWS ヘッダを信用せず、設定で定めた許可アルゴリズム集合に含まれることを確認してから使う (`alg: none` / アルゴリズム混同攻撃)
8. JWS ヘッダの `kid` が hello の `kid`、および取得した JWK の `kid` と一致すること

`iss` / `aud` の比較を前方一致・部分一致にしないこと。`wss://r.example.evil` を弾くためであり、かつ origin 単位の比較は相乗り時に別インスタンスを取り違えるため (§4.2)。

### 5.8 ack と送信開始

S は ack を受けるまでメッセージを送ってはならない。R は ack より前に届いたメッセージを受けた場合、その接続を close する。

ack は信頼確立の通知ではない (S 側は接続時点で R を TLS により信頼している)。R が受け入れ準備を終えた時点を S に知らせるための合図である。

これがないと R は検証完了前に届いたメッセージをプールする必要が生じ、バッファ管理・サイズ上限・タイムアウトという要らない複雑さを抱える。ack を境界にすれば、早すぎるメッセージは単にプロトコル違反として捨てられる。

### 5.9 推奨値

| 項目 | 値 | 根拠 |
|---|---|---|
| proof の有効期間 (`exp` まで) | 10 秒 | ハンドシェイクは同一リージョンなら数十〜数百 ms で完了する。これを満たせない相手との通信は元より成立しない |
| `challenge` 長 | 128bit 以上 | 予測不能であればよい |
| `kid` 長 | 128bit 以上 | 同上 |
| 許可 `alg` | EdDSA (Ed25519) を既定とし、集合として設定に持つ | 単一固定にする必然性はない。移行時に 2 つ許可できる必要がある |

`exp` を短くできるのは、本プロトコルが接続確立時の 1 回しか署名を使わないため。長い有効期間を必要とする場面がない。

`exp` は絶対時刻なので両者の時刻同期に依存する。ただし新鮮さの担保は challenge が負っているため、スキューによる失敗は可用性の問題であって安全性の問題ではない。厳しすぎて落ちるなら緩めてよい。

## 6. 鍵と challenge の交換 (C2)

R が `iss` に対応する設定内 URL へ C2 を張り、`kid` の鍵を要求すると同時に challenge を渡す。応答を受けたら閉じる。

本プロトコルが規定するのは手順の意図であり、URL の形やメッセージ形式ではない。以下の性質が満たされていれば、具体的な規約は実装側で決めてよい。

共通要件:

- 要求に `kid` と `challenge` を載せる
- 応答は単一の鍵を返す
- C2 (R が dial する接続) を使う。C1 上で要求すると循環し、攻撃者が自分の鍵を返して自分の署名を通せる。信頼の根は認証対象の接続の外側になければならない
- 認証前の生の接続なのでレート制限を入れる

challenge をここに載せるのは、C2 が鍵取得のために元々必要だからである。challenge のためだけの往復は発生しない。

S は challenge を受け取った時点で proof を作り、C1 上で送る。jwk_res は C2 に、proof は C1 に返る。

### 6.1 HTTPS

`iss` のパス配下に `kid` 単位で置く。具体的な URL の形は規定しない。要件は §6.3 を満たすこと、すなわち `iss` ごとに鍵空間が交差しないことだけであり、パス構成は実装の都合で決めてよい。

```
iss: wss://h.example/mesh/a
key: https://h.example/mesh/a/jwk/<kid>   ← 一例
```

challenge は要求ボディに載せる。応答は単一 JWK (`application/jwk+json`)。未知の `kid` には 404。

### 6.2 専用 wss (取得後即 close)

`iss` のエンドポイントに dial し、`kid` を指定して要求する。

```
R ──▶ S   dial (R は TLS サーバ証明書で S を認証)
R ──▶ S   jwk_req { kid, challenge }
S ──▶ R   jwk_res { jwk } / 不存在
R ──▶ S   close
```

WebSocket は HTTP と違い要求と応答が framing 上で対にならないため、応答も自己記述的である必要がある。`jwk_res` を型として持つのはこのため。

ws 上のメッセージ形式は規定しない (CBOR / JSON / 既存の mesh メッセージ型のいずれでもよい)。

HTTP サーバを別に立てずに済むぶん実装コストが低い。ハンドシェイクのコストは HTTPS と実質同じ。

### 6.3 同一 origin 相乗り時の分離 (必須)

鍵の取得先はインスタンスごとに分離しなければならない。

`wss://h.example/a` と `wss://h.example/b` が origin 単位の共通鍵空間を共有すると、こうなる。

1. b が自分のエフェメラル鍵をその空間に登録する
2. b が `iss: wss://h.example/a` と名乗って R に接続する
3. R は a の鍵取得先を引き、b の鍵で検証に成功する

`iss` の検証は、その `iss` に対応する鍵空間が分離されて初めて意味を持つ。

これは規約の形ではなく満たすべき性質である。取得先を `iss` のパス配下に置く、`iss` のハンドラ自身に応答させる、といった構成はいずれも構造的にこれを満たす。origin 単位の固定パスや全インスタンス共通の鍵ストアを選んだ場合にのみ、分離を別途作り込む必要が生じる。

## 7. 鍵のライフサイクル

鍵は wss セッションに従属する。接続ごとに生成して使い捨てるため、ローテーションという概念を持たない。

```
生成 ─▶ kid 採番 ─▶ 署名送信 ─▶ [R が取得・検証] ─▶ ack 受信で破棄
                                 └─ この間 取得可能 ─┘
```

- 破棄契機は ack 受信、またはセッション終了のいずれか早い方
- 鍵はセッションのライフサイクルに載る。セッションが消えれば一緒に消えるため、独立した寿命管理を持たない
- 生存数は同時ハンドシェイク数に等しく、自然に上限が付く
- 秘密鍵はメモリ上のみ。プロセスが死ねば消える

`exp` は鍵の寿命とは無関係で、R 側でハンドシェイク段階の寿命を区切るためだけに存在する (§5.4)。

## 8. 接続管理

各ノードは全ピアに対して対等に dial する。

### 8.1 glare (同時接続競合)

A と B が同時に dial すると 2 本張られうる。両方を確立させ、それぞれ §5 の検証を通したうえで一方を close する。

> `iss` 文字列を比較し、小さい側が dial した接続を残す。

2 本は認証状態として対等なので、どちらを残すかに優劣はない。要件は両者が同一の結論に達することだけであり、そのために規則を固定する。

畳む前に両方検証しておくことで、残る 1 本が認証済みであることが保証される。

close には glare 由来と分かる close code を用いる。相手にとっては正常系であり、再接続契機にしてはならない。

### 8.2 再接続

接続断時の再接続はアグレッシブにやる必要がない。相手が復旧すれば起動時にこちらへ dial してくるため、復帰の検出は相手の起動をトリガに即時となる。バックオフは緩くてよい。

### 8.3 その他

- ハートビートは必須 (中間 box による無通知切断の検出)
- ピア除名は確立済み接続に反映されない。認証が接続時 1 回である以上、除名時は該当接続を明示的に close する経路が要る

## 9. 適用範囲外

- ステートレス / リクエスト単位の通信 (P1 違反)。接続単位の信頼確立という前提が消えるため、メッセージ単位署名 + リプレイウィンドウ + 鍵キャッシュという別方式になる。鍵を使い捨てにできなくなり、ライフサイクル設計から変わる
- TLS 終端より内側の区間の完全性 (§4)。運用側の責務
- 権限分離、およびホストを掌握された正規ピア (§4.1)

## 10. テスト

信頼の根が Web PKI であるため、PKI レイヤとプロトコルレイヤを分離してテストする。前者は正常系のみ、後者は PKI を成立させた上で網羅する。両者が揃って初めて漏れがない。

### 10.1 テスト用 PKI の作り方

`insecure_skip_verify` に相当するフラグを実装に持ち込まない。設定ミスやフラグの伝播で本番で有効になる事故が定番であり、検証を迂回するコードパスの存在自体が最大の脆弱性になる。

代わりに、テスト用 CA を信頼ルートに注入する。ワンタイムで CA を生成し、それをルートに加えたうえで正規の検証経路を通す。迂回路が存在しないまま、任意の証明書でテストできる。

ハーネスの初期化で以下を発行しておく。

| 証明書 | 用途 |
|---|---|
| ノード用 (複数、SAN 違い) | 正常系および別ノードのなりすまし |
| 期限切れ | PKI 失敗系 |
| 別 CA 署名 | PKI 失敗系 |

### 10.2 PKI レイヤ

PKI の失敗はすべて接続失敗であることを確認する。個別の理由を区別する必要はない。

- 期限切れ証明書 → 失敗
- 別 CA 署名の証明書 → 失敗
- SAN が接続先ホストと不一致 → 失敗
- 正規の証明書 → 成功

### 10.3 プロトコルレイヤ

PKI を成立させた上で、以下がすべて close に至ることを確認する。

| ケース | 対応する規定 |
|---|---|
| `ver` が未知 | §5.7-1 |
| `iss` が設定にない | §5.7-2 |
| `aud` が自分以外 | §5.7-3 |
| proof の `iss` / `aud` が hello と異なる | §5.7-4 |
| `challenge` が不一致 | §5.7-5 |
| `challenge` の再利用 (同一 challenge で 2 回) | §5.5 |
| `exp` 経過後の proof | §5.7-6 |
| 署名が鍵と対応しない | §5.7-7 |
| `alg` が許可集合外 | §5.7-7 |
| `alg: none` | §5.7-7 |
| proof の `kid` が hello の `kid` と不一致 | §5.7-8 |
| 取得した JWK の `kid` が proof の `kid` と不一致 | §5.7-8 |
| ack より前のメッセージ送信 | §5.8 |

正常系として、hello から ack までが完走し、以降のメッセージが受理されることを確認する。

### 10.4 境界ケース

PKI が全成功したうえで失敗すべきケース。PKI レイヤのテストでもプロトコルレイヤのテストでも拾えないため、独立して書く。

- 同一 origin 相乗り (§6.3)。同一証明書・同一ホストで `/a` と `/b` を立て、b が `iss: .../a` を名乗ると弾かれること。b の鍵で a の署名が検証できてしまわないこと
- 自己識別 (§5.2)。相乗り構成で `/a` 宛の hello を `/b` に送ると弾かれること。`self` がハンドラごとに正しく束縛されており、Host ヘッダの偽装で揺らがないこと
- 鍵取得の循環 (§6)。認証対象の接続上で鍵を要求した場合に拒否されること
- `iss` / `aud` の部分一致 (§5.5)。`wss://r.example.evil` および origin が同じでパスが異なる値が弾かれること
- glare (§8.1)。A と B が同時に dial したとき、両者が同一の接続を残す結論に達すること。1 本に畳まれ、残った接続が認証済みであること

### 10.5 状態の非残存

本設計は管理対象を増やさないことを目的としており (§1)、その性質が実装で保たれているかをテストで固定する。ここを書いておかないと、後からタイマーやキャッシュが足される。

- ack 受信後に S 側の鍵が破棄されていること (§7)
- セッション破棄時に鍵が破棄されていること (§7)
- 消費済み challenge が R 側に残っていないこと (§5.5)
- ハンドシェイク完了後、リプレイ記録に相当する状態が存在しないこと
- 同時ハンドシェイクを N 本張って完了させた後、鍵の生存数が 0 に戻ること

## 11. 既知の同等物

OAuth 2.0 の `private_key_jwt` クライアント認証 (RFC 7523 / OIDC Core) と同型。`iss` = クライアント識別子、`aud` = 相手のエンドポイント、短い `exp`、公開鍵は pull 配布、という構造が一致する。

差分は 2 点。鍵をエフェメラルにして集合ではなく `kid` 単位で配る (`private_key_jwt` は長命鍵を JWKS URI で配ることを想定)。および `jti` の代わりに受信側発行の challenge を使う。ステートフル接続では、鍵取得の往復に相乗りさせられるため、追加のコストなしにリプレイ記録が不要になる。

## 12. 検討し、採用しなかった選択肢

認証方式:

| 方式 | 不採用の理由 |
|---|---|
| mTLS | 証明書の配布・更新という管理対象が増え、§1 に反する。加えて CA/B Forum ballot SC-081 により public CA の clientAuth EKU が廃止済み (Let's Encrypt は 2026-07-08 に発行終了)。private CA の運用が必須になる |
| Noise IK | 相手の静的公開鍵を事前共有する前提。管理したくないものを管理することになり §1 と真逆 |
| Noise XX | 事前共有は不要だが、交換した鍵を FQDN に紐づける仕組みが別途必要。それが結局 PKI なら TLS の上に重ねる二度手間 |
| WireGuard | 各ノードの公開鍵を全ピア設定に書く必要があり、§1 に反する |
| 公開鍵の設定直書き | 最も単純だが、ピア増減のたびに全ノードへの設定配布が発生する。§1 そのものに反する |
| SPKI pinning | 信頼の根は浅くなるが、ピン値の配布と更新という管理対象が生まれる。§1 に反する |

鍵配布:

| 方式 | 不採用の理由 |
|---|---|
| JWK Set での配布 | 集合を返すと同時接続数が外部から観測できる。鍵が要るのはハンドシェイク相手だけなので `kid` 単位で配る |
| `/.well-known/` 固定パス | エンドポイント URL を知らない相手が origin から辿るための規約。本プロトコルでは `iss` がエンドポイント URL そのもので、それを設定として持っているため探索が不要 |
| RFC 8414 / OIDC Discovery の `jwks_uri` 経由 | メタデータを引いてから鍵を引く間接参照。URL を設定に持つ以上ラウンドトリップが 1 回増えるだけ |
| 鍵の長命化 + キャッシュ | 保存場所と復旧手順という管理対象が生まれる。キャッシュの利得は接続時 1 回の取得に対して小さい |
| 鍵破棄の TTL 管理 | ack があれば破棄契機が確定するため、タイマーは不要な複雑さ |

ハンドシェイク:

| 方式 | 不採用の理由 |
|---|---|
| challenge を独立した往復で送る | C2 が元々必要なので、そこに相乗りさせれば往復が増えない (§6)。また C1 の確立直後に R から送ると、mesh の通信路上で認証の文脈が S の名乗りより先に始まる |
| TLS exporter (RFC 9266) | challenge を不要にできるが、TLS 終端がアプリケーション自身である構成を要求する。§4 の信頼境界を狭め、LB 終端を許さなくなる |
| `jti` + 受信側リプレイ記録 | 記録の保持と期限管理という状態が増える。ステートフル接続なら challenge を接続に従属させたほうが状態が消える |
| ack なしでの送信開始 | R が検証完了前のメッセージをプールする必要が生じる。バッファ管理・上限・タイムアウトを抱え込む |

接続管理・テスト:

| 方式 | 不採用の理由 |
|---|---|
| dial 責務の割り当て (ID の小さい側だけが dial する等) | 責務を持つ側が落ちている間、生きている側から復帰させる手段がなくなる |
| `insecure_skip_verify` 相当のテスト用フラグ | 検証を迂回するコードパスが本番バイナリに残る。テスト用 CA をルートに注入すれば同じことが迂回路なしでできる (§10.1) |

## 付録: 攻撃と対策

| 攻撃 | 対策 |
|---|---|
| 第三者によるなりすまし | TLS + JWS 署名検証 |
| 正規ピアによる署名転送 (リレー) | `aud` 完全一致 |
| 署名のリプレイ | R 発行の `challenge` |
| 相乗りインスタンスの取り違え | `iss` / `aud` をパス込み完全一致、鍵空間の分離 (§6.3) |
| アルゴリズム混同 / `alg: none` | `alg` を許可集合と照合してから使う |
| SSRF | 鍵取得先を設定値に限定 |
| 鍵取得の循環 | 取得は C2 で行う |
| 接続数の外部観測 | 集合を公開せず `kid` 単位で配る |
| 鍵取得を突く DoS | レート制限 |
| 鍵漏洩 | エフェメラル + メモリのみ + 使い捨て |
