# DR-0015: 外部の完了を待つものは全て非同期にする (原則)

Status: Accepted (2026-09-14。kawaz 裁定)
Date: 2026-09-14
Sponsor: kawaz (2026-09-14)
関連: 監査 `docs/findings/2026-09-14-blocking-io-audit.md`、issue `2026-09-14-async-io-principle-and-blocking-io-audit`、issue `fold-from-head-with-versioned-cache`、契約 CT-Q8 (`docs/QUESTIONS.md`)、[DR-0010](DR-0010-one-topic-mechanism-one-egress-layer.md)

## 1. 背景

instance は 1 プロセスで全ての接続に答える。受信側に接続ごとの直列化は無く (`src/transport/driver.ts` は frame ごとに `void handle(frame, conn)` で呼ぶ)、ハンドラが `await` で譲る限り他の frame は進む。この構造が効くのは、譲るものが譲った時だけである。同期の読み書きはイベントループそのものを止めるので、その間は同じ接続の他の op も、他の接続も、topic の flush も、watcher の callback も、mesh の heartbeat も進まない。**1 箇所の同期呼び出しが止めるのは 1 接続ではなく instance 全体である。**

## 2. 決定

**メモリと CPU だけで完了する処理だけが同期で、それ以外 (ファイル、ネットワーク、プロセス、エージェント応答、承認、lock など外部の完了を待つもの全て) はプロトコルも実装も非同期にする。** CPU だけでも長い処理 (巨大な JSON の parse、大きいファイルの走査) はイベントループを塞ぐので、同期でよいのは短く終わるものに限る。

### 2.1 「IO」はファイルとネットワークに限らない

外部の完了を待つブロッキング待ち全般を指す。エージェントへの依頼の応答待ち、子プロセスの結果、承認、lock の取得がすべて同じ枠組みに入る。ここで言う「止まる」にも 2 つある — イベントループが塞がることと、直列化のガードや待ち行列で後続が進めなくなることで、どちらも外部の完了を 1 つの待ちに束ねている点で同じものである。対して、メモリ上の情報を返すだけの req/res (`hello.session` / `hello.user` の同期応答、既に読んである値の snapshot) は同期でよい。

### 2.2 直すのはハンドラ単位ではなく経路単位

経路のどこか 1 つに同期呼び出しが残れば、その経路を非同期にした効果は消える。op の入口から fs 呼び出しまで、あるいは topic の値を作る入口から読みまでを丸ごと直す。「ハンドラは async だが、その先の 1 関数が同期に読む」は直したことにならない。

### 2.3 まとめ処理は承認なしに入れない

batching / 窓集約 (時間窓での集約、複数の要求を 1 つの運命共同体にすること) を kawaz の承認なしに入れない。所要時間がばらつく要求を束ねると、短いものが長いものに巻き込まれる。総時間が多少伸びても、1 要求 = 1 単位で個別に答える方を採る。承認を求める時は「何が束ねられ、最悪ケースで何が何に巻き込まれるか」を書く。

要求ごとの相関は既に土台にある (`request_id` が全 Request / Response に載り、daemon は同一接続の要求を並行に実行する) ので、個別に答えるために足すものは無い。

### 2.4 同期でよいもの

- **起動時・停止時に 1 回だけ走るもの**。接続を握る前、または全部手放した後なので、待たされる相手がいない
- **CLI の単発コマンド**。プロセスが 1 コマンドで終わる
- **CPU だけで固定コストのもの** (mesh の ephemeral 鍵生成など)

書き込みの順序が意味を持つものを非同期にする時は、前の書き込みの完了に次を連ねて順序を保つ。順序の保証を捨てる言い訳に非同期化を使わない。

## 3. 不採用

| 案 | 理由 |
|---|---|
| 同期でよい範囲を「小さいファイル」「速い呼び出し」で線引きする | 速さは環境の性質であって処理の性質ではない。小さい追記 1 回でも、遅いディスクや競合の下ではイベントループを止める。判定できる線は「外部の完了を待つか」だけ |
| 遅い op だけ非同期にし、速い op は同期のまま残す | 止まるのは instance 全体なので、速い op が止める相手は速い op ではない。経路に 1 つ残れば効果が消える (§2.2) |
| 遅い処理を複数応答に分割して返す | 遅い op が他を待たせないのは並行 dispatch が担保している。1 要求 = 1 応答を崩す理由が無い |
| ばらつく要求を窓で集約して一度に返す | 短い要求が長い要求に巻き込まれる。読む側は束で読むわけではない (§2.3) |

## 4. 影響

- 監査 (`docs/findings/2026-09-14-blocking-io-audit.md`) が (C) に分類した箇所は、この原則の適用対象として直す。fold の seed (`src/transcript/tail.ts`) は issue `fold-from-head-with-versioned-cache` の設計と一体で直す
- topic の「値を述べる」入口が Promise を返す形になる範囲は、開始応答で値を述べないまま開くことを契約が許すか (CT-Q8) の裁定に従う
- ユーザ指定の正規表現のようにイベントループを塞ぐが非同期化では解けないものは、別の手段 (worker / 子プロセスへの追い出し、パターンの制限) の判断に回す。issue `session-search-regex-unbounded`
