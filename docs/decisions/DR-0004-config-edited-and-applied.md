# DR-0004: 設定は編集用と適用用に分け、検証を通った値だけを適用する

Status: Accepted (2026-09-12。kawaz 裁定。TS ローダー化そのものは 2026-09-11 の裁定)
Date: 2026-09-12
Sponsor: kawaz (2026-09-11/12)「編集用と適用用を分ける」「検証 NG でも前回 OK で起動する」
関連: 設計 §8.2 (設定)、§8.3 (起動の順序)、§8.4 (常駐)、[DR-0013](DR-0013-instances-are-long-running.md)、issue `2026-09-11-ts-config-loader`

## 1. 背景

設定は当初 JSON + マージ規則だったが、深いマージと浅いマージの境界が設定項目ごとに違い、「この項目はどちらで合流するか」を規則表 (`MERGE_RULES`) が持っていた。規則表は設定項目が増えるたびに増え、読み手は値を見ても実効値が分からない。

同時に、設定ファイルを人が編集する場所と、instance が読む場所が同じだった。編集の途中で構文エラーのある状態が disk にあり、その瞬間に instance が再起動すると、セッションを捌いている instance が typo 1 つで消える。

## 2. 決定

### 2.1 編集用と適用用を分ける

**編集用** (人が触る、`${XDG_CONFIG_HOME:-~/.config}/ccmsg/`):

| ファイル | 何か |
|---|---|
| `config_v2.ts` | `({builtin, config}) => config` — このホストの全 instance が出発点にする値 |
| `endpoints.json` | `[{id, endpoint}, …]` — mesh の全 instance (自分も他ホストの分も) |
| `supervisor.json` | `{instances: ["<id>", …]}` — このホストが起こす instance |
| `instances/instance-<id>.ts` | `({builtin, default, config}) => config` — instance 1 つ分 |
| `ccmsg-config_v2.d.ts` | TS ファイルが書き当てる型宣言 (`daemon add` が置く) |

**適用用** (人は触らない、`$CCMSG_STATE_DIR/config/`): 検証を通った値 `satisfied.json` と、その由来になった各ファイルのコピー。**監督者と instance はここだけを読む。**

**通らなかったものは適用用に到達しない。評価は 2 度行われない** — 走るのは検査した値であって、その値を作ったファイルの 2 度目の読み直しではない。

### 2.2 起動と reload は常に同じ 1 本の pass

編集用を全部読む → JSON は構文と schema、TS は import して関数を実際に呼ぶ (**設定関数は Promise を返してよい。ローダーは常に await する**) → ファイル単位で自分だけで言えるところまで検査する (間違いが作られた場所で報告されるように) → 最後の関門は全体としての整合 (監督者が起こす id が mesh の行と設定ファイルの両方を持つ、endpoint の重複、port と config home の衝突、設定関数が `endpoints` を書き換えていないこと) → 全部通ってから state 側に書き、起動 / reload する。

`daemon add` / `daemon remove` も編集用を書いた後にこの同じ pass を通る。

### 2.3 通らなければ前回適用した値で起動する

**state 側は触らない。** 何がどこで間違っているかを log と `ccmsg daemon status` に出し、ホストは前回適用された値から起動する。セッションを捌いている instance を、ファイルの typo が奪ってよいものではない。**例外は初回だけ** — 戻る先が無い。

### 2.4 mesh はデータで、設定関数のものではない

`endpoints.json` は全ホストで同じ 1 つのリスト。instance は自分の id でその中の自分の行を見つけ、それが自分の endpoint になる (peer が dial する先、handshake の `iss` / `aud`、人に渡すページの URL)。**設定関数はこのリストを読んでよいが、違うリストを返したら config error**。リストに無い id は住所が無いので起動を拒む。

これにより **`self` の probe は不要になった** (DR-0001 §2.7 が probe で確定するとしていた自分の endpoint は、自分の id の行から読む)。

### 2.5 マージ規則は無い

設定ファイルには「その 1 段上の全体」が渡され、「自分が使う全体」を返す。`config.dump.presets = […]` は置換、`.push(…)` は追加で、どちらのつもりかはファイル自身が言う。渡される `builtin` / `default` は deep freeze され、`config` はその可変コピー。

誰も持っていないフィールドは読み込みを止める。綴りを間違えたフィールドは「書いたのに効かない設定」であり、それが黙って無い状態で起動するのは §8.3 が拒む状態そのもの。

### 2.6 反映は起動時に 1 度だけ

無再起動での反映 (hot reload) は持たない。instance ごとの設定は小さく、再起動は安い (永続するのは 6 種だけ)。

### 2.7 `ccmsg config` が両側を突き合わせる

`list` (各ファイルが何で、何が間違っていて、適用済みのコピーと差があるか) / `diff [file]` / `diff --satisfied` (適用したら全体が何が変わるか) / `show` (編集用を評価して `satisfied.json` の形で表示、書き込まない) / `revert <file> | --all` (適用済みのコピーで上書き。上書きされる方は `$CCMSG_STATE_DIR/config.rejected/<相対パス>.<時刻>` に退避し、その場所を必ず表示)。

`show` と `diff --satisfied` が設定関数を呼ぶので、**設定関数は副作用を持たない前提**。

### 2.8 バックアップ対象は名指しのパスだけ

設定ファイルが import する先は対象外 (制限として明記)。管理外が壊れても `satisfied.json` があれば起動は守られる。

### 2.9 ファイル名の `_v2` は v1 との同居のため

`config_v2.ts` / `ccmsg-config_v2.d.ts` の名は、v1 系と同じホストに同居する期間があることによる。v1 が居なくなったら改名できる。

## 3. 不採用

| 案 | 理由 |
|---|---|
| JSON + マージ規則 (`MERGE_RULES`) | 項目ごとの合流規則が増え続け、値を見ても実効値が分からない |
| hot reload (無再起動での反映) | 反映のために mtime 監視 / reload / 配線し直しが要る。再起動は安い |
| 壊れた config で、その機能を無効にして起動を続ける | 「設定したつもりの機能が黙って効いていない」状態が runtime まで持ち越される |
| 壊れた config で起動を止める | セッションを捌いている instance を typo が奪う。前回の値で起動する方が、可用性と「黙って効かない」の両方を満たす |
| state 側で TS を再評価する | 検査した値と走る値が別になる |
| `self` を config に持つ | 自分の id で mesh の行を引けば分かる。`self` を書かせると「どれが自分か知らずに同じリストを配れる」性質が壊れる |

## 4. 影響

- 設計 §8.2 / §8.3。§8.3 の「壊れた config は起動失敗」は本 DR の §2.3 に置き換わる (config が名指した資源の解決に失敗した時に起動を止めるのは残る)
- DR-0001 §2.7 の「自分の endpoint は probe で確定する」は本 DR §2.4 に置き換わる
- `MERGE_RULES` と JSON config は撤去済み
